# GitHub 好玩榜

**把 GitHub 上好玩的项目挑出来，用大白话告诉你是干什么的、你到底装不装得上。**

GitHub 是一个放公开项目的地方：全世界的人把自己写的软件放在上面，谁都可以下载来用。
问题是它太大了——每天都有成千上万个新项目，你不可能一个个点开看。这个项目就是替你干这件事的：
它去把值得看的项目挑出来，分成三个榜，每个项目都告诉你"这是干什么用的""你要动手到什么程度"。

拿到的就是**一个网页**：打开它，看三个榜，挑一个你感兴趣的，照着说明把它跑起来。

## 它长什么样（没有截图，但你看得见）

打开页面，最上面是三个可以点的标签，就是三个榜：

- **🔥 本周飙升**——最近大家在玩什么。回答的是"这周有什么新鲜好玩的"。
- **🌟 新手能玩**——里面全是"今晚就真的能装上"的项目。回答的是"我这种没开过命令行的人，能玩哪个"。
- **🏆 经典必玩**——GitHub 上早就有的好东西，很多人用过，说明和教程通常更多。给刚来的人补课用。

每个项目是一张卡片，上面写着：项目名、一句话说明、它是用什么写的、有多少人收藏了它，
还有两个小徽章——一个是**你要动手到什么程度**：

- 🟢 **一键就能玩**：有现成的安装包，下载下来双击就行，不用碰命令行。
- 🟡 **要几步**：得先装个东西、再敲一两行命令。
- 🔴 **要懂点技术**：得自己动手编译，或者先把它那套环境搭起来。

另一个是**有没有中文说明**（🈶 有中文说明 / 只有外文说明）。

点开一张卡片，会从右边滑出一个详细面板：它是干什么的、你需要先准备什么、第一条命令是什么、
点一下就复制走，还有"它为什么会上这个榜"。

页面底下还能换一天看——之前采集过的每一天都留着。

**它是一堆纯静态网页**：没有后台、没有数据库、不用登录、不会向任何地方发送你的信息。
它只做一件事：读项目目录里那几个 JSON 数据文件，然后把它们显示出来。

## 它跟别的"GitHub 热门榜"有什么不一样

市面上已经有一批同类项目（`bonfy/github-trending`、`SnailDev/github-hot-hub`、
`antonkomarev/github-trending-archive`、`isboyjc/github-trending-api`、`git-trends.github.io`、
`vitalets/github-trending-repos` 等等）。它们做的是同一件事：把 GitHub 趋势页面上的条目按天搬下来，
存成 Markdown / JSON / RSS。这些项目很有用，但这个项目想补三个它们都没做的空缺：

1. **它们不自己算"这周涨了多少收藏"，我们算。** 大家抄的都是趋势页面上那两个数字；一旦页面改版或那个数字
   变了，谁也验证不了。我们自己把每天的情况存下来，靠前后两次记录的差值算出真实的增长
   （详见下面的"三轴与 100 分"）。
   顺带说一句为什么这件事难：GitHub 从不公布收藏的历史曲线，官方那套"按收藏事件排序"的数据源自己也在退化。
   所以**谁自己攒着历史，谁才有资格诚实地谈"暴涨"**。
2. **它们不评价"新手能不能真的装上"。** 十万收藏量级的中文榜单（比如 HelloGitHub）质量很高，
   但都只告诉你"这是个好东西"，不写怎么装、不标难度。这个项目把"你要动手到什么程度"当成一等公民。
3. **它们是给开发者看的。** 这个项目的全部文案都是大白话，还带一页`新手准备页`，
   专门教从没打开过命令行的人怎么开始。

做：三轴挑项目 + 大白话 + 保姆级中文说明 + 纯静态可发布的网站 + 公开可查的每日数据。
不做：第 N 个趋势页面搬运工。

## 三轴与 100 分（大白话版）

前两个榜（本周飙升、新手能玩）会给每个项目打分，满分 100 分，由三部分组成：

| 这一轴 | 满分 | 它在问什么 |
|---|---|---|
| **热度** | 45 | 这一周新增了多少人收藏它？（一周涨到 3000 就是满分，涨得越多分越高，超过就封顶。） |
| **口碑** | 30 | 这个项目靠不靠得住？把它拿去改造的人多不多、最近还在更新吗、近 90 天发过新版本吗、有没有开源许可证、收藏还在涨吗。 |
| **新手友好** | 25 | 你真的装得上吗？安装方式越简单分越高（有现成的 Windows 安装包 18 分、一条命令 16 分、要先装 Python 14 分、要先装 Node 8 分、只能自己编译 6 分、只能在容器里跑 4 分、找不到安装方式 0 分；按**最容易的那一种**算，不是几种相加），另外有**中文**说明文件就给 7 分、没有就是 0 分（不按比例；代码里那一项的构成是"正文 4 分 + 本地化文件 3 分"，满足任一就给满 7 分）。**非中文的本地化说明不给这一项的分**：只有日文/韩文说明的项目这一项是 0 分，也只会被如实标成"有本地化文档（非中文）"。 |

- **🔥 本周飙升**：过门槛的项目，按三轴总分从高到低排。
- **🌟 新手能玩**：同一批项目，换成按"新手友好"那一轴从高到低排（总分不看）。
- **🏆 经典必玩**：**不算分、也不套门槛**，只按总收藏人数排。所以里面可能有已经停止维护的老项目。

"过门槛"指的是这五条同时成立：没有停止维护、有开源许可证、最近 7 天内有更新、总收藏人数不少于 200、
至少有一条我们核实过的安装方式。缺一条就不进前两个榜。

（还有一条"不是纯资料清单"——那种"我收集了一堆链接"的项目也确实进不去。但它**不是第六道独立的门槛**：
资料清单的判定本身就要求"没有任何已核实的安装方式"，而那已经被上面第五条挡掉了。
换句话说，它只是给同一批被挡下的项目一个更准确的说明，不会让任何**多**出来的项目落榜。）

**没问到的事不扣分**：有些项目的发版信息和增长情况我们确实没查到，那时给一半的分数，
只有明确知道"没有"才记 0 分。新项目不会因为"还没有历史"而吃亏。

完整口径（每一项的算法、降级顺序、每个数字的出处怎么看）在网站上那一页
[`public/about.html`](public/about.html) 里，也在设计文档
[`docs/superpowers/specs/2026-10-10-github-app-store-design.md`](docs/superpowers/specs/2026-10-10-github-app-store-design.md) 里。

## 30 秒跑起来（第一次用电脑上的"命令行"？看[中文使用手册](docs/使用手册.md)）

前提：电脑上装了 Node.js 22 或更新的版本（命令行里敲 `node -v`，能打出版本号就是装好了）。
没装的话，[中文使用手册](docs/使用手册.md)里有从头到尾的步骤。

```bash
git clone https://github.com/<你的账号>/github-hotspot.git
cd github-hotspot
npm run demo
```

第三条命令跑完会打印一个地址，用浏览器打开它就能看到整站。**这条命令不联网、也不用先采集**：
它用的是仓库里自带的一份演示数据，页面上会明明白白写着"这是演示数据（示例）"——
它只是让你看看这个网站长什么样，不代表最近真的在流行什么。

> 没有 `git`、或者不想装它？在仓库页面上点绿色的 **Code → Download ZIP**，解压到任意文件夹，
> 然后跳过第一条命令——先 `cd` 进那个文件夹，再跑 `npm run demo` 就行（这一点手册里也写了）。

想看到**你自己电脑上采集出来的真实数据**，把第三条换成：

```bash
npm start
```

（第一次打开会看到"还没有任何榜单数据"——因为数据得先采集一次，见下。）

## 四条命令分别干什么

| 命令 | 要不要联网 | 它会做什么 |
|---|---|---|
| `npm run demo` | **不要** | 用仓库自带的演示数据起本地预览，页面上标注"这是演示数据"。想先看效果就跑它。 |
| `npm run collect:offline` | **不要** | 用内置样本把完整流程跑一遍，产出写进你自己的数据目录 `public/data/`，页面上同样标注"这是演示数据"。 |
| `npm run collect` | **要** | 真的去 GitHub 采集。会写 `public/data/YYYY-MM-DD.json` 和一份 `daily/` 日报。耗时几分钟到十几分钟（每一条都是串行请求、失败会退避重试）。 |
| `npm start` | **不要** | 本地预览，读的是 `public/data/` 里的真实采集产物。 |

关于 `npm run collect`，有几句实话要先说：

- **它需要联网**，并且要访问 `raw.githubusercontent.com`（读项目的说明文档）。只有 `api.github.com`
  通、这一个域名不通时，采集能跑完，但"有没有中文说明"这类信息会拿不到。
- **不登录 GitHub 时有额度限制**：整轮采集自己设了 **45 次请求**的上限；其中搜索接口另外有更严的限制。
  额度用完时这一轮会**主动收工**并如实标注"这一期数据不完整"，而不是静默超支或者编数据。
  想跑得更宽裕，可以设环境变量 `GITHUB_TOKEN`（GitHub 的个人访问令牌）。
- **它不会自己跑。** 数据是**你敲命令那一刻**采的。仓库里带了一个**可选的**每日定时任务
  （`.github/workflows/daily.yml`），但它**只在 GitHub 上生效**，详情见下一节。

## 想让它每天自己采一次？仓库自带一个可选的工作流

`.github/workflows/daily.yml` 是一份现成的 GitHub Actions 工作流：每天 UTC 23:00 跑一次采集，
把结果提交回仓库，于是线上站点就有了新数据。

关于它，有五件事必须说清楚（前四件都是 GitHub 的既定行为，不是这个文件能改的）：

1. **它只在 GitHub 上生效。** 它不会跑在你的电脑上——本地始终是你亲手敲 `npm run collect`。
   不启用它的时候，榜单只在你手动采集之后才更新。
2. **要在仓库设置里允许 Actions 写入。** 默认情况下 `GITHUB_TOKEN` 对仓库内容只有读权限，
   而提交采集产物需要写权限。工作流里已经显式声明了 `permissions: contents: write`；
   如果仓库或组织把 "Workflow permissions" 设成了只读，那一步会被拒
   （报 `Resource not accessible by integration`），需要到
   Settings → Actions → General → Workflow permissions 改成 "Read and write permissions"。
3. **别人 fork 之后默认不会自动跑。** GitHub 为了防止无谓的运行，会**默认禁用** fork 里的定时任务，
   必须在那个 fork 里手动启用才会跑。另外公开仓库连续 60 天没有任何活动时，GitHub 也会自动把它停掉。
4. **它的额度够用**：这个工作流用的是 GitHub 自动提供的 `GITHUB_TOKEN`，把 core 额度从
   "未登录的 60 次/小时"提到 **1000 次/小时/仓库**，而本项目一轮采集的预算是 **45 次请求**。
   就算不配 token 也跑得完（45 ≤ 60），只是余量小、遇上重试容易半路收工。
   GitHub 官方也说明：定时任务在高峰期可能被推迟，所以执行时间会有偏差。
5. **随时可以手动跑一次**：工作流带了 `workflow_dispatch`，GitHub 的 Actions 页面里会有
   一个「Run workflow」按钮。

（上面第 2、3 条的原文出处是 GitHub 官方文档：
[REST API 的额度](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
与 [schedule 事件](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)。）

不想用它也完全可以删掉这个文件——删掉之后一切照旧，只是不再有人替你定时采。想在自己电脑上定时采，
就用系统的计划任务（Windows 的"任务计划程序"、macOS/Linux 的 `cron`）自己排一条。

## 三个榜为什么空着 / 我该看什么

- 刚克隆下来时 `public/data/` 里**什么都没有**（这个目录被 git 忽略了），所以 `npm start` 会诚实地说
  "还没有任何榜单数据"。想看效果用 `npm run demo`；想让当前这个网页有数据，跑一次
  `npm run collect:offline`（不联网）或 `npm run collect`（联网）再刷新。
- 榜单里出现"这一周的新增收藏，我们没有查到"是正常的：那个数字我们确实拿不到时就不写数字，
  绝不会用 0 冒充"没涨"。

## 一次采集会在哪里留下东西

```text
public/data/YYYY-MM-DD.json        某一天完整的三个榜单（网站读的就是它）
public/data/index.json             有数据的日期列表
public/data/history/YYYY-MM.json   按月存的归档快照（写着，但现在没有任何代码读它）
daily/YYYY-MM-DD.md / .json        给人看的日报
data/cache.json                    本地缓存，少问 GitHub 几遍
```

`public/data/` 与 `data/` 都被 git 忽略了，`daily/` 没有被忽略。这两件事的实际差别是：

- **被忽略的那些（`public/data/` 里的文件、`data/cache.json`）`git status` 不会显示，
  也不会被 `git add .` 收进去**——想提交它们，只能用 `git add -f`（仓库自带的那个每日工作流就是这么做的）。
- **`daily/` 里的日报没有被忽略**，所以 `git status` 会直接列出来，`git add daily` 就能提交。

所以"想让采集产物变成公开可查的历史"这件事，对 `public/data/` 而言**不是 `git add .` 能自动完成的**，
要么手动 `git add -f`，要么照着下一节改 `.gitignore`。

## 发布到网上（可选）

整站是纯静态的，任何静态托管都能放。**核心那一步是：把 `public/` 目录作为发布目录**，
因为 `index.html`、`app.js`、`style.css` 和 `data/` 都住在它下面。

但有件事必须先想清楚：**`public/data/` 被 git 忽略了**，而静态托管是从你的 git 仓库构建的。
所以光把代码推上去，线上站点打开只会显示"还没有任何榜单数据"。要让线上有内容，三选一：

- **让采集产物进仓库**：把 `.gitignore` 里那一行 `data/` 改成只忽略缓存文件
  （也就是把那一行换成 `data/cache.json`；**注意文件里写的就是 `data/`，没有前导斜杠**）：

  ```diff
   node_modules/
  -data/
  +data/cache.json
   fixtures/last-good/
  ```

  改完之后再往仓库里加一次数据文件（第一次要手动加，因为它们过去被忽略过）：

  ```bash
  git add public/data && git commit -m "把榜单数据放进仓库"
  ```

  这就是"公开可查的每日历史"的做法。（为什么 `data/` 这一行会连 `public/data/` 一起忽略：
  `.gitignore` 里不带前导斜杠的目录名会匹配**任意深度**的同名目录。所以改这一行，两处一起生效。）
- **用仓库自带的每日工作流**：`.github/workflows/daily.yml` 跑完这一次采集就会把
  `public/data/` 提交回仓库（用 `git add -f`，不看 `.gitignore`），所以线上站点在**这一次运行结束之后**
  就有内容了。它需要你在仓库设置里允许 Actions 写入（见上面那一节）；
  另外要留意：它在**启用后的第一次**运行里，若联网采集一条内容都没拿到，会保留仓库里已有的数据、
  不会凭空产出内容；仓库里原本没有数据时，线上就还是空的。
- **换个发布方式**：在托管平台上跑构建命令 `npm run collect`，让它在部署时现采一次
  （这需要平台能联网、并且要在环境变量里配 `GITHUB_TOKEN`，否则额度很紧）。

三家都免费够用，选一个就行：

- **GitHub Pages**：仓库 Settings → Pages → Source 选 "Deploy from a branch"。它只能选分支的
  根目录或 `/docs` 目录，而本项目要发的是 `public/`——所以最省事的做法是另建一个 `gh-pages` 分支，
  把 `public/` 里的文件放到那个分支的根目录，然后发布它。
- **Cloudflare Pages**：新建项目 → 接上仓库 → Build command 留空（或填 `npm run collect`）→
  **Build output directory 填 `public`**。
- **Vercel**：新建项目 → 接上仓库 → Framework Preset 选 "Other" → Build command 留空（或填
  `npm run collect`）→ **Output Directory 填 `public`**。

## 已知限制（都不是"以后再补"的客气话，是现在真的做不到）

- **联网采集这条路没能在开发这台机器上端到端验证过**：这台机器访问 `raw.githubusercontent.com` 会超时，
  所以 `npm run collect` 的完整联网路径是**读过代码 + 有单元测试**，但不是在这里真跑通的。
  采集流程本身用内置样本跑通并验证过（`npm run collect:offline`）。
- **浏览器里的行为只验证到"显示逻辑"这一层**：这个项目把所有"该显示什么"的判断都放在
  `public/render.mjs`（不碰浏览器、纯函数，能被 `node --test` 直接断言），所以那些判断是有测试的；
  但开发这个项目的环境里起不了浏览器，**没有人真的用鼠标点过整站一遍**。第一次用的时候建议自己点一遍。
- **没有安装器、没有本地探测**：这个网站是纯静态页面，它看不到你的电脑——你装没装 Node、Python，
  它一概不知道，也不会去猜。要确认只能你自己敲 `node -v` 看一眼。
- **月度归档文件现在是个空头支票**：`public/data/history/YYYY-MM.json` 每次采集都会写，
  但**目前没有任何代码读它**。它只是留着以后用的档案，不是一个功能。
- **那个每日工作流没有在真实仓库里跑过**：`.github/workflows/daily.yml` 的结构有测试盯着
  （触发、权限、命令、`git add -f`、推送都要在），但本机没有 GitHub 仓库可挂，所以
  "它在 Actions 里真的跑成了"这件事**没人验证过**。第一次启用后请到 Actions 页面看一眼那次运行。
- **本开发环境的限制，不是项目的问题**：这个项目自己的测试在普通电脑上是正常通过的——
  在项目目录里敲 `npm test` 就行。但本项目**开发时所处的受限环境**不允许 `node --test` 为每个测试文件
  派生子进程，于是那里会报 `spawn EPERM`；那种环境下改用
  `node --test --test-isolation=none test/*.test.mjs`（不派生子进程，同一批用例）。

## 开发这个项目

零运行时依赖，只用 Node 自带的能力；没有构建步骤、没有数据库、没有大模型。
需要 Node ≥ 22。

```bash
npm test                              # 跑全部测试（node:test，无第三方测试框架）
node --test --test-isolation=none test/*.test.mjs   # 不派生子进程（本项目开发环境里用这条）
npm run collect:offline               # 不联网跑一遍完整采集流程
node fixtures/demo/seed.mjs --write   # 重新生成仓库里自带的那份演示数据
```
